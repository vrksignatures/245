# Customers-list execution audit

Line numbers below refer to the **original** Java source inside `SudhaAutoBot_Upgraded.zip` at commit `80443080`, before these changes. They are not line numbers in the modified archive.

## What the code proves, and what it does not

* **A definite failure for `SMR 2157`:** `FloatingPanelController.java:181–190,625–640` stores the text through `RunHistory.setTyped`. `RunHistory.java:177–185` uses `RetailerPolicy.normalizeAnyId` (uppercase and trim only), so the ledger is set to `SMR 2157` at `RunHistory.java:211–230`. `StartPoint.java:189–214` and `RetailerSequence.java:108–136` compare that string to the displayed `SMR2157` without removing internal spaces. Thus the seeker does not reach the last ID and the sequence asks to scroll to it. At the bottom, `SudhaAccessibilityService.java:2198–2211,2282–2293` calls `restartFromTop`, clears the last ID and presses Back. The older `StartPoint.normalise` did remove spaces, but was not used by the panel or `RunHistory`.
* **For exactly `SMR2157`, no single device-specific cause is provable from the repository alone.** Given correctly parsed, unblacklisted cards `[SMR2157, 20173, …]`, `seesAnyId` reaches the first, and `decideAnyId` explicitly selects `20173`. `UpgradeSelfTest.java` tested only those preconstructed ID strings, not the real accessibility parser or service. A device accessibility-tree dump and logcat are necessary to distinguish the failure modes below; claiming the exact phone tree is known would be speculation.
* `AccessibilityTree.java:241–325` is an SMR-only scanner. The original service initializes `rows` from it (`SudhaAccessibilityService.java:1988`) and replaces those rows with structural rows **only if** the expanded-card condition and nonempty `parseVisibleCards` hold (`2030–2058`). If parsing fails entirely but old SMR rows are found, the scanner silently drops numeric cards. When no row after the last is visible, the sequence scrolls; a missed last ID causes the Back described above. If some cards parse and others do not, the service silently uses only the successfully parsed subset, with the same risk.
* `DistributorBlueprint.java:34–35,137–179,186–224,337–375` accepts only a restricted 24-character ASCII ID pattern, detects container labels using literal `"customer id"` despite its whitespace-tolerant regex, and falls back to the closest label within 140 pixels without proving it belongs to the same card. Split labels use the next nonempty text without proving it is the ID. Container traversal and geometric matching depend on the actual tree. Case alone (`Id` versus `ID`) is already handled; spacing, partial nodes, long IDs, punctuation and mixed card hierarchies are not reliably handled. A fallback click can ascend into a list-wide clickable ancestor (`AccessibilityTree.java:206–225`).
* `SudhaAccessibilityService.java:2048–2054` applies a **permanent ID blacklist** even to freshly identified genuine retailers. A stale or incorrectly learned entry can suppress `20173` or any other ID regardless of its current card and adjacency. `DistributorBlueprint.java:94–102` also filters by blacklisted ID rather than by card position. Cross-page distributor-name carry is applied on every poll, not just across an actual page change, and can exclude a non-adjacent namesake.
* `SudhaAccessibilityService.java:1889–1901,4174–4178`: with no visible header, normal inspection requires three detected cards, or one only after *the bot itself* has scrolled. START on a manually pre-scrolled screen with one or two parsed numeric cards may be unrecognized. The normal unrecognized path pauses after a timeout rather than pressing Back. During return-to-list (`1746–1799`), a page with no recognized header or parsed cards can instead receive repeated Back presses. `total customers` is also used for both Home and list recognition.
* `SudhaAccessibilityService.java:2360–2409` verifies details by substring search over the entire screen; after four ticks it can continue even without any ID match. Its fallback ID scanner is SMR-only. This can act on the wrong numeric customer, or fail to attach the numeric customer when resuming on details. `RetailerPolicy.java:33–43` additionally imposed a 32-character limit. `StartPoint.java:29–34`, legacy `Seeker.sees`, `RetailerSequence.decide`, `ScrollMemory.Seek.next`, `AccessibilityTree` and `AccountId` contained prefix-based legacy logic. The live paths used the parallel `*AnyId` methods; the Aakriti roster and UI-molding heuristics also used `AccountId` for informational counts/learning. `Roster.java:209` discarded non-SMR IDs when restoring its seen set.

## Original execution flow

1. Reset invokes the panel reset callback, clears the ledger and start history (`SudhaAccessibilityService.java:1254–1273`). START ends editing and persists the box (`FloatingPanelController.java:181–190,625–640`).
2. `startRun` (`SudhaAccessibilityService.java:696–747`) loads configuration and today's ledger, calls `RunHistory.atStart`, resets run counters, sets running, and schedules inspection. A pending order takes the recovery route instead. `RunHistory.atStart` sets `lastHandled`, without marking it processed, and creates the seeker. `WorkflowStateMachine.beginRetailer` merely accepts the ID and moves to DETAILS (`WorkflowStateMachine.java:54–59`).
3. `inspect` checks the target package, loading, return-to-list, notifications/dialogs and pending recovery, then Home, list, details, history and form (`1701–1932`). A list can be identified from its header, the old SMR row count, or parsed structural cards, subject to the thresholds described above. The loading check already excludes a wide horizontal progress bar (`4119–4153`); it is not an explanation for this Customers-list reproduction.
4. `onRetailerList` detects expansion, classifies structural cards and filters persistent blacklist IDs; it then calls the seeker, optionally scroll memory, and the displayed-order selector (`1974–2169`). If `SMR2157` and `20173` are both present in the eligible structural rows, the seeker marks rows through `SMR2157` DONE_BEFORE without moving the last position (`StartPoint.java:189–224`, `DailyLedger.java:239–252`); scroll memory sees the last ID and does not burst (`SudhaAccessibilityService.java:960–1008`); `decideAnyId` returns `20173` and the click is dispatched. `DailyLedger` accepts numeric IDs, stores last/pending/results, and guards duplicate processing (`DailyLedger.java:174–278`).
5. If the last ID is absent, `decideAnyId` returns `SCROLL_TO_LAST`; if present with no eligible subsequent row, it returns `SCROLL_FOR_MORE`. The list scroller tries accessibility scrolls and drags and judges movement (`ListScroller.java`). Scroll memory can replay recorded scrolls when there is no active seeker and last is not already visible; its live path is `nextAnyId` (`SudhaAccessibilityService.java:960–1044`, `ScrollMemory.java:198–242`). At the end it either restarts from Home, makes a one-time sweep for missing work, or completes (`SudhaAccessibilityService.java:2170–2250`). A detected end is not proof that all rows were parseable.

## All original global Back dispatch sites

* `506`: already-ordered notice after recording the retailer.
* `605`: empty order-list / persistent blank order page after recording skip.
* `1796`: bounded return-to-list walk, including a misclassified list; it first tries dismissing dialogs and waits for busy screens.
* `2291`: `restartFromTop`, called when last was not found at list end or when doing the one-time incomplete-count sweep.
* `2764`: `abandonRetailer` after recording an error.
* `3991`: `onPlaceOrderUnanswered` after recording an unverified submission.
* `4095`: `goBackTo`, called by mismatch, empty history and copy/no-data abandonment paths. Success and generic skip enter `returningToRetailerList`, which can later reach `1796`.

These Back paths are conditional; the provided reproduction does not establish which fired on the phone.

## Changes and limitations

* The live list uses only structurally classified cards, recognizes a single visible card even at START, does not use the persistent ID blacklist to reject present retailers, and stops if any visible delivery-point anchor cannot be read. ID labels are case/whitespace tolerant; IDs are not restricted by character class or length. Split ID values must be on the label's row. The safe container traversal does not pair an ID with a different card by proximity and does not climb to a list-wide click target. This can stop instead of proceeding on an unfamiliar hierarchy; a phone dump is needed to extend it safely.
* START resolves a whitespace-only difference to the visible ID if the match is unique on that page, preferring exact identity. Punctuation and numbers are not rewritten. A last ID not found at the end now stops instead of pressing Back and forgetting the position. Each card, rather than a permanent ID blacklist, is classified for adjacent distributor/shadow exclusion. A cross-page carry is tied to page changes and not re-applied blindly on the same page.
* Details verification now requires an exact customer ID in a parenthesized header or labelled ID, excluding distributor lines; absent verification stops instead of processing. The existing horizontal-progress-bar exclusion is preserved. The live roster receives structural retailer IDs. Legacy SMR-oriented public helpers remain for older model tests, but no longer drive the live list or details paths; `UiMolder` and legacy `AccountId` heuristics still exist for UI-learning/informational behavior.
* Structural adjacency is inherently unprovable when the preceding card is off-screen at START, or when a scroll jumps over cards with no overlap. The code cannot guarantee “always” skip a hidden adjacent shadow without the missing tree/list context. Similarly, a failed ID parse now pauses instead of guaranteeing progress. These require real-device verification, not an assertion based on synthetic fixtures.
* The repository's active CI entry point is `.github/workflows/main.yml`; `.github/workflows/build-apk.yml` is **inside the zip**, not at repository root. The extracted project's `tools/selftest/run.sh` passes with JDK 17 runtime and Eclipse Java compiler 3.33. The sandbox has no Android SDK or Gradle and cannot reach their download hosts, so `assembleDebug` and GitHub Actions were **not run**. No real-phone or full Android execution was available.
